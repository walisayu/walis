# Jenkins 與 Woodpecker 的缺點盤點

這份不是選型比較，是**盤點別人踩過的坑**，用來決定 Walis 要補什麼、以及刻意不做什麼。
外掛機制的設計筆記在 `docs/plugins.md`，兩份要一起看：盤點的結論會改變外掛的優先順序。

## Jenkins

Java 寫成，外掛（`.hpi`）載進同一個 JVM，更新中心約 1,900+ 個。

| 缺點 | 根因 | 對 Walis 的意義 |
| --- | --- | --- |
| 一個外掛可以拖垮整台 controller | 外掛與 core 同一個 JVM，**沒有沙箱** | 外掛必須跑在受限的直譯器裡，且只能回傳資料 |
| 依賴地獄與版本相容矩陣 | 外掛之間可以互相依賴 | **不允許外掛互相依賴** |
| 升級常常打爛既有外掛 | 擴充點介面沒有版本承諾 | manifest 帶 `apiVersion`，硬檢查 |
| CVE 不斷，多數來自外掛 | 外掛有完整系統存取權 | 能力由 manifest 宣告並經管理員核准 |
| UI 技術債（Jelly + Stapler） | 外掛可以自己畫頁面 | **不開放 UI 擴充**，只給宣告式參數表單 |
| Freestyle 與 Pipeline 兩套模型長期並存 | 沒有及時汰換舊模型 | 只維持一種任務模型 |
| Groovy Sandbox 的核准疲勞 | 白名單太細，動不動就要人按同意 | 權限粒度用「能力」而不是「方法」 |
| 資源吃重、啟動慢 | JVM 與外掛數量 | 保持單一執行檔與 SQLite |

Jenkins 的價值也很清楚：**幾乎任何工具都有現成整合**。它的缺點幾乎全部來自
「外掛可以做任何事」這個決定——這正是它強大與脆弱的同一個原因。

## Woodpecker CI

Drone 的分支，Go 寫成，server + agent，流程定義在 repo 裡的 `.woodpecker.yaml`。

已向官方文件確認的兩點（見文末來源）：

- **必須連接 Git forge**（GitHub、Gitea、Forgejo、GitLab、Bitbucket、Bitbucket DC），
  認證與專案清單都來自 forge；不在清單內只能自己寫 addon forge。
- **外掛就是容器映像**，設定透過步驟的 `settings` 注入，由 agent 從 registry 拉取。
  文件明講外掛「只應該允許作者預期的功能」，用來跟「可以跑任意指令的步驟」區隔。

| 缺點 | 根因 | 對 Walis 的意義 |
| --- | --- | --- |
| 沒有 Git forge 就用不了 | 認證與專案模型都綁在 forge 上 | **Walis 不要走這條路**：本機腳本、維運工作、沒有 repo 的任務都要能跑 |
| 實務上等於要求 Docker／K8s | 容器是工作的基本單位 | 容器化應該是**選項**而不是前提 |
| 寫一個外掛要建置並發布映像 | 外掛即映像 | 外掛應該是「貼一段程式碼」等級的門檻 |
| 流程只能寫 YAML，改 CI 要 commit | 設定即程式碼是唯一路徑 | 保留 UI 編輯，但補上匯出／版控的路 |
| 沒有第一級的產物儲存 | 產物要自己推到外部儲存 | Walis 的 `ArtifactStore` 是優勢，維持 |
| 權限來自 forge 的 repo 權限 | 沒有自己的 RBAC | 自有帳號體系是優勢，但角色仍嫌粗 |
| 版本間設定格式有過破壞性變更 | 早期迭代快 | 任務定義的結構變更要有搬遷路徑 |
| 除錯較難（每步都是容器） | 隔離的代價 | 隔離要做成可調整的等級 |

Woodpecker 值得抄的兩點：**每一步都是獨立步驟**（有自己的狀態與日誌），
以及 `woodpecker-cli exec` 可以在本機跑同一份流程——後者對「改了腳本要驗證」非常有用。

## 兩者的共同教訓

1. **隔離等級決定了外掛能開放給誰。** Jenkins 無隔離 → 只能靠人工審核；
   Woodpecker 用容器 → 可以放心跑陌生人的映像。Walis 想「讓別人開發上傳」，
   就必須先決定隔離手段，否則外掛機制只能停留在「自己人用」。
2. **強制的前提會趕走使用者。** Jenkins 強制 JVM 與外掛生態，Woodpecker 強制 forge 與容器。
   Walis 現在最大的差異化就是「沒有前提」——不需要 repo、不需要容器、不需要 runtime。
   任何補強都不該犧牲這點。
3. **擴充點的介面比擴充點的數量重要。** 兩者的痛苦都來自介面沒有版本承諾。

## Walis 當時的缺口與後續處理

盤點當下的結論是「問題不在外掛，而在更底層」。下表是當時的清單與後來的處理：

| 缺口 | 當時狀況 | 現況 |
| --- | --- | --- |
| **沒有步驟概念** | 一個任務 = 一段 shell | **已補**：`BuildSteps` 與 `BuildStepSequence`，每步驟獨立狀態與日誌，本機與遠端共用同一份迴圈 |
| **建置沒有任何隔離** | 讀得到 Walis 自己的資料庫 | **已補安全預設**：工作目錄／連結／重疊檢查與環境白名單；macOS 使用 `sandbox-exec`；沒有 OS 沙箱的平台預設以未隔離方式執行並在建置日誌註明，管理員可以改成要求隔離邊界（沒有邊界就拒絕執行，或使用外部隔離 runner） |
| 設定不在版控 | 只有稽核紀錄 | **已補**：`/api/portability` 匯出匯入，動作流程在檔案裡是物件 |
| 無法在本機試跑 | 只能整個任務跑 | 部分：外掛可以預覽產生的腳本；整份流程的本機試跑還沒做 |
| 權限粒度粗 | 只有三種全站角色 | **已補**：任務層級的 `ViewRole` 與 `RunRole`（`RunRole` 下限是 operator，viewer 永遠只能看） |
| 沒有 multibranch／PR 任務 | webhook 只比對固定分支 | 未做 |
| 沒有快取機制 | 只有清空開關 | **已補**：任務層級的 `CachePaths`，先清空再還原 |
| 通知管道與 AI 供應商寫死 | 在 dispatcher 內分支 | 部分：外掛機制已經有了，但只做了 `action` 擴充點 |
| 無指標端點 | 只有 `/health` | **已補**：`/metrics`，Prometheus 格式 |
| 單機、重啟中斷建置 | 標記失敗不能續跑 | 未做（定位就是單機） |

另外補上的（不在原本的清單裡，但同樣來自這次對照）：**平行步驟**、**矩陣建置**、
**API 金鑰與 MCP server**——最後這項讓 AI 代理可以像用 Jenkins 那樣觸發建置、等結果、讀日誌。

## 補強順序

**P0 — 步驟化。** 把「一個任務一段腳本」改成「一個任務多個步驟」，每步驟有自己的
狀態、日誌、耗時與結束碼；失敗時可設定中止或續行。理由：重試、平行、快取、
以及**外掛要掛在哪裡**全部建立在步驟邊界上。現在動作流程編譯成單一腳本的做法
在這個方向上是死路——動作一旦要回傳結構化結果，就需要步驟邊界。

**P0 — 建置隔離的最小版本（已完成安全預設）。** 工作目錄、cache、artifact 與受保護根目錄
會先做 allowlist、realpath、連結與重疊檢查，子程序環境採白名單；macOS 使用 `sandbox-exec`。
沒有可用 OS 沙箱的平台不會靜默降級，必須改用外部隔離 runner，或由管理員明確接受未隔離風險。

**P1 — 設定可攜。** 任務定義能匯出／匯入 JSON，再考慮支援 repo 內的設定檔（**可選，非強制**）。

**P1 — 外掛機制。** 依 `docs/plugins.md` 的規劃走，但介面等步驟化定案再定。

**P2 — 快取、平行、matrix、指標端點、per-job 權限。**

## 刻意不做

- **強制綁 Git forge**（Woodpecker 的路）：Walis 要能跑沒有 repo 的維運工作。
- **強制容器**：容器化是選項，不是前提。
- **UI 擴充外掛**（Jenkins 的路）：純負債。
- **外掛市集、外掛互相依賴、HA**：先把單機做好。
